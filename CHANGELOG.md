## 2026-10-01
- Fixed negative/irrelevant reviews being showcased as top allergy evidence — user spotted a live hotel card quoting "The moment I lay on the comforter, my face broke out in a terribly itchy allergic reaction" under a "✅ Allergy-conscious reviews from real guests" badge and a bogus "Allergy score: 4.8/5". Root cause in `classifyAndExtract()` (duplicated in `hotel-search`, `restaurants-search`, `content-pipeline`): a review tripping `WARNING_PHRASES` ('unsafe', 'reaction', 'allergic reaction', 'anaphylaxis', 'epipen'...) scored *highest* of any category (0.95, above genuine positive safety evidence at 0.9) once paired with any dietary term — so an actual allergic-reaction incident, or even a completely unrelated complaint that only matched on the bare word "unsafe" (a harassment complaint, a "sketchy neighborhood" comment), could become a place's top-billed, maximum-scored quote. Fixed by excluding any `hasWarning` match from evidence entirely (`if (hasWarning) return null`) in all three functions — a warning signal is never positive proof, full stop. Deployed to Supabase (hotel-search v76, restaurants-search v80, content-pipeline v44); live-tested (Bangkok hotel search now returns only genuine positive snippets, no warning-phrase matches, and the original offending hotel no longer qualifies).
- Cleaned up the DB rows already corrupted by the bug before the fix: found 21 hotels + 7 restaurants whose stored `allergy_score` was exactly `4.8` (the fingerprint of the old `score = 0.95` path) with a warning-phrase snippet as their only evidence and no other source to fall back on. Deleted those 26 hotel_sources + 7 restaurant_sources rows and nulled the corresponding `allergy_score` — these are rendered directly (not re-fetched) on prerendered article pages (`ArticleDetail.tsx` → `TopHotelsSection`/`HotelCard`), so the bad quotes/scores were live on the site until this ran, not just a future-facing risk. `HotelCard` already falls back gracefully when `quote`/`allergy_score` is absent, so no UI changes were needed.
- Found a second, deeper layer of the same bug: an article's own prose (`seo_articles.content_markdown`) is written once by `generateArticle`/`generateRestaurantArticle`, which feeds the LLM each hotel/restaurant's raw `hotel_sources`/`restaurant_sources.raw_text` and asks it to paraphrase or quote it directly — so a bad warning-phrase excerpt generated before this fix could already be baked into an article's narrative, independent of the hotel-card evidence above. Checked all 8 published articles referencing one of the 28 affected hotels/restaurants; 4 had real warning language in the body text, the worst being `food-allergy-bangkok-hotels` — an entire single-hotel article built around the Hilton Garden Inn Bangkok Silom's allergic-reaction quote from the original report, now with zero valid evidence at all. Manually rewrote 3 articles' `content_markdown` in place (same `id`/`slug`/`published_at`, only the prose and `hotel_ids`/`restaurant_ids` changed) following the exact same real-evidence-only rule the generation prompt enforces: `food-allergy-bangkok-hotels` now covers 5 real Bangkok hotels with genuine positive evidence (dropped the Hilton, added Conrad Bangkok, Bangkok Marriott Sukhumvit, and the 3 newly-discovered clean hotels from this fix's live test), `tallinn-food-allergy-guide` dropped GO Hotel Shnelli (keeping Hilton Tallinn Park and Citybox Tallinn, both genuinely evidenced), and `food-allergies-reykjavik-guide` dropped Harry's Seafood and Grill (keeping its other 12 restaurants). The 4th article's "warning" match (`food-allergies-bangkok-restaurants-guide`) was a false positive — a guest reporting *no* allergic reaction, i.e. genuinely positive evidence — so left untouched.
- Fixed `social-poster`'s Instagram posting: `food-allergies-bangkok-restaurants-guide` had been stuck 23 days straight, failing daily with "Media ID is not available" (OAuthException 9007/2207027). Root cause: Instagram's media container is created asynchronously (Meta fetches/processes the image in the background), and the old code called `media_publish` immediately after `media` create with no wait — publishing before the container finished processing. Added `waitForMediaReady()`, which polls the container's `status_code` (up to 10× 2s) until `FINISHED` before publishing. Deployed directly to Supabase; verified live — Bangkok's Instagram post went through on the next manual run (14s total, including the wait).
- Removed fabricated guest-quote testimonials across all 22 live `src/data/destination-*.ts` static pages (London, Paris, New York, Rome, Madrid, Amsterdam, Tokyo, Toronto, Cyprus, Crete, Rhodes, Ayia Napa, Athens, Barcelona, Portugal, Swiss Alps, Thailand, Koh Samui, Stockholm, Turkey, Abu Dhabi, Hotel Chains, Cruise Lines, Gluten-Free Europe, Italy, Eilat, Warm Winter) — the same "never fabricate content" violation CLAUDE.md already documents once from `TopHotelsSection.tsx`, except this was ~10x the scope and never caught by that earlier fix. Extracted and checked all 154 hardcoded `quote`/`guestReview` fields: the `Hotel`/`Restaurant` type doesn't even have a source/author field, 38 of them carried an outright invented name ("- Sarah J.", "- David R., USA"), and `destination-amsterdam.ts`'s 10 quotes each claimed a fake citation on top of that ("(Source: Marriott Reviews)", "(Source: Hilton Guest Reviews)"...). Built a standalone, read-only, one-off verification tool (`verify-quote` Edge Function — deliberately *not* merged into `hotel-search`/`restaurants-search`/`content-pipeline`, no DB writes, no shared code path, so it couldn't regress any live process) that looks up each named hotel/restaurant on Google Places and runs the same (already-fixed) `classifyAndExtract()` against its real reviews. Of 134 live entries (20 in `destination-generic.ts` were dead code, deleted outright — unused, unimported, and had the same fabricated-name pattern), 19 had genuine, verifiable evidence and were replaced with the real review text (no fabricated attribution, matching the project's existing "a guest wrote" convention); the other 115 had no qualifying real evidence and had their quote removed entirely rather than replaced with anything invented. Regression-tested `hotel-search`/`restaurants-search` before and after this work (unchanged, unaffected) since neither was touched. `verify-quote` retired (stubbed to a 410, since no tool here can actually delete an Edge Function) now that the one-off job is done.

## 2026-09-17
- Fixed the Netlify Deploy Preview failure that was blocking PR #23 (and would have blocked any PR): `netlify/functions/translate-card.js` was orphaned dead code — the real translation feature was migrated to `supabase/functions/translate-card/index.ts` (called via `supabase.functions.invoke('translate-card', ...)` in `translationService.ts`; the only other reference was a stale debug-panel code snippet, not a real call) — but Netlify still bundles every file under `netlify/functions/` on every build regardless of whether it's called, and this one was CommonJS (`module.exports`) while `package.json` declares `"type": "module"`, so bundling crashed the entire build. Fixed the same way `sitemap.cjs` already does in this repo: renamed to `translate-card.cjs`. Confirmed unrelated to this PR's own changes — same failure reproduced identically on two different commits, and the file/package.json weren't touched by either.
- Fixed the real, live cause of the "Page with redirect" indexing issue Search Console has been failing to validate since 09-08 (34 affected pages and growing): the site's own primary navigation — `MainMenu.tsx`'s menu items, `constants/home.ts`'s `HOME_CONTENT.navigation.menu.items` (feeding `Footer.tsx`'s "Quick Links"), `Footer.tsx`'s "Popular Destinations" links, and `FeaturedDestinations.tsx` on the homepage — all hardcoded internal `<Link>`/`<a>` hrefs *without* the trailing slash (e.g. `/destinations/paris` instead of `/destinations/paris/`). Since the host 301-redirects every one of those to the slash form, Google's crawler kept rediscovering and re-crawling the no-slash variant from the homepage and global footer/nav on every visit — the highest-traffic, most-frequently-crawled surfaces on the whole site — which is exactly why Search Console's fix validation kept failing instead of resolving: the canonical fix from 09-07/09-08 corrected where each page *points*, but never touched where the site's own navigation *links from*. Found by reading the user-supplied Search Console screenshot's affected-URL examples (all matching known hardcoded destinations like London/Paris/New York), then grepping the whole `src/` tree for every literal `to="/..."`/`href="/..."` missing a trailing slash — 25 occurrences across 13 files, now all fixed. `scripts/verify-seo.mjs` only checks each page's own canonical tag against its own URL; it doesn't check that other pages' links point at the canonical (trailing-slash) form, so this class of bug wasn't caught by the existing regression guard — worth a follow-up if it recurs.
- Fixed the real cause of Facebook going quiet since 09-13 while Instagram kept posting daily: `social-poster` picked one shared "oldest incomplete on either platform" article per day, and a backlog of 6 older articles (Montreal through Bangkok) that already had Facebook but were only missing Instagram happened to occupy every single day's pick since 09-13 — so Facebook's own gap (Seoul, then Dubai/Rio/Sydney/Lima, none of which had been attempted at all) never got touched. Changed to two independent oldest-first picks per run, one per platform, so neither platform's backlog can starve the other.
- Found and fixed an unrelated bug while investigating: `social-poster.yml`, `pinterest-poster.yml`, `content-pipeline.yml`, `gsc-report.yml`, `linkedin-poster.yml`, and `backfill-hero-image.yml` all wrote the Edge Function's JSON response into the job summary via `echo '${{ steps.call.outputs.body }}'` — a title or caption containing an apostrophe (e.g. "Vancouver's Best Restaurants") breaks out of the single-quoted string and crashes that step, marking the whole run as failed in the GitHub Actions UI even though the actual post/pin/article already succeeded before that step ran. Fixed by passing the body through an `env:` variable instead of interpolating it directly into the shell script.
